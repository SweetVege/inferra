# Deploying Inferra

Four managed services, all with free tiers:

| Piece | Service | Notes |
|---|---|---|
| Web (Next.js) | Vercel | Serves the UI and proxies `/api/*` to the API, so session cookies stay first-party |
| API + worker | Render (Docker) | One container: FastAPI, the job worker, and the scheduler |
| Metadata database | Neon (Postgres) | Workspaces, runs, insights, reports, schedules |
| File storage | Cloudflare R2 (S3-compatible) | Uploaded datasets as Parquet, extracts, trained models |

Deploy in this order: each step needs a URL or key from the one before.

## 1. Postgres on Neon

1. Create a project (any region close to your Render region).
2. Copy the connection string from **Connect**. It looks like
   `postgresql://USER:PASSWORD@HOST/neondb?sslmode=require`. Use the direct (non-pooled) string.

## 2. Storage on Cloudflare R2

1. **R2 → Create bucket**, for example `inferra`. Keep it private.
2. **R2 → Manage API tokens → Create API token**: permission *Object Read & Write*, limited to that bucket.
3. Note the **Access Key ID**, the **Secret Access Key**, and the S3 endpoint
   `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`.

## 3. API on Render

1. **New → Blueprint**, pick this repository. Render reads `render.yaml` and creates `inferra-api`.
2. Fill in the variables it asks for:

   | Variable | Value |
   |---|---|
   | `INFERRA_DATABASE_URL` | the Neon connection string |
   | `INFERRA_WEB_ORIGIN` | for now `https://example.com`; you set the real Vercel URL in step 5 |
   | `INFERRA_S3_BUCKET` | `inferra` |
   | `INFERRA_S3_ENDPOINT_URL` | `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` |
   | `INFERRA_S3_ACCESS_KEY_ID` / `INFERRA_S3_SECRET_ACCESS_KEY` | from R2 |
   | `INFERRA_LLM_MODEL` / `ANTHROPIC_API_KEY` | a Claude model id and an API key, or leave empty (see below) |
   | `INFERRA_DAILY_RUN_LIMIT` | agent runs per person per UTC day, e.g. `3` (`0` or unset: no limit) |
   | `INFERRA_RUN_ALLOWLIST` | optional: comma-separated GitHub logins allowed to start runs (empty: everyone signed in) |
   | `INFERRA_GITHUB_CLIENT_ID` / `INFERRA_GITHUB_CLIENT_SECRET` | leave empty until step 6 |

   `INFERRA_SECRET_KEY` is generated by Render. Keep it stable: it signs sessions and derives the
   demo report's public link.
3. Choose a plan. **Free** works, but the service sleeps after 15 minutes without traffic: the first
   visit then waits about a minute, and schedules only fire while it is awake (a due schedule runs
   once when it wakes). **Starter** stays up, which suits scheduled monitors.
4. Deploy. On every start the container applies migrations, builds the demo workspace if it is
   missing or out of date, and serves. Check `https://<your-api>.onrender.com/api/health` returns
   `{"status":"ok"}`.

Without a model the whole demo works (it was produced by the real pipeline with a scripted model),
but new agent runs are disabled and the UI says so. With a model, each run costs a few cents to
tens of cents in API usage, depending on the model and the workflow.

**Anyone who signs in with GitHub can start runs on your API key.** Before setting the key:

- set a monthly spend limit in the Anthropic Console, as the backstop;
- set `INFERRA_DAILY_RUN_LIMIT` (scheduled re-runs count against the person who created the
  schedule), and, to keep runs to yourself and people you invite, `INFERRA_RUN_ALLOWLIST`.

Everyone can still sign in, upload data, and browse; only starting runs is limited. The Ask page
shows how many runs are left today, or why runs are unavailable.

## 4. Web on Vercel

1. **Add New → Project**, import this repository.
2. **Root Directory:** `apps/web`. The framework preset is detected as Next.js.
3. **Environment variable:** `INFERRA_API_URL` = `https://<your-api>.onrender.com` (no trailing
   slash). Set it before the first build: the `/api` proxy is fixed at build time, so changing it
   later needs a redeploy.
4. Deploy, and note the production URL, e.g. `https://inferra.vercel.app`.

## 5. Point the API at the web origin

On Render, set `INFERRA_WEB_ORIGIN` to the Vercel URL (no trailing slash) and let it redeploy.
Sign-in redirects and the GitHub callback are built from this value.

## 6. GitHub sign-in (optional; the demo works without it)

1. GitHub → **Settings → Developer settings → OAuth Apps → New OAuth App**.
2. Homepage URL: the Vercel URL. Authorization callback URL:
   `https://<your-web>/api/auth/github/callback`.
3. Generate a client secret, then set `INFERRA_GITHUB_CLIENT_ID` and `INFERRA_GITHUB_CLIENT_SECRET`
   on Render. Signed-in users get a personal workspace plus read access to the demo.

## 7. Check it

- Open the Vercel URL → **Explore the demo workspace**: runs, the shared report, the monitor.
- Demo → **Reports → Weekly product review** shows the report's public link. It stays the same
  across deploys, so it can go in a README or a CV.
- With GitHub configured: sign in, upload a CSV, and (with a model set) ask a question.

## Operations

- **Updates.** Pushing to `main` redeploys both services. Migrations run on start; the demo
  rebuilds itself when a release changes it.
- **Scaling the worker.** The API runs the job worker and scheduler in-process. To split them, set
  `INFERRA_INLINE_WORKER=false` on the API and add a Render background worker with the same image,
  the same variables, and the command `python -m inferra.worker`. Several workers are safe: jobs are
  claimed with `SKIP LOCKED` and schedules with a compare-and-set.
- **Custom domain.** Add it in Vercel, then update `INFERRA_WEB_ORIGIN` and the GitHub OAuth app.
